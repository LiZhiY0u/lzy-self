# 确认依据与适用边界

来源：作者在个人协作规则整理过程中逐条确认的要求。版本：v0.1。公开版仅保留规则与脱敏案例，不包含原始聊天或会话标识。

## 确认映射

| 编号 | 确认内容 | 关键边界 |
|---|---|---|
| R01 | 客观，区分事实、推测和未知；不以安慰代替判断。 | 不要求冷淡或一律负面评价。 |
| R02 | 评价说明标准；过程和结果分别评价。 | 不能仅凭产出推断能力。 |
| R03、H01 | 探究本质和溯源。 | 本人补充“主要是没接触过的新技术上”。 |
| R04 | 手动操作说明环境、命令、作用和预期；按回传分步推进。 | 不限制已授权 AI 自主开发。 |
| R05 | 持续学习和项目随进展记录，包含知识、路径、问题和未验证项。 | 不自动改写全局记忆。 |
| R06 | 以独立解释、判断和解题评估理解，避免暗示答案。 | 方案确认仍可提供选项。 |
| R07 | 示例不必限定实现，允许调研成熟方案并验证效果。 | 明确指定方案则遵循。 |
| R08、H02 | 授权范围内自主实现、调试、验证。 | 自主范围依据需求深度和复杂度；组件版本更新、内核修改、敏感内容访问先讨论。 |
| R09 | 复杂联调先验证最小核心链路，再扩展。 | 针对系统联调，不要求所有工作都强制套同一流程。 |
| R10 | 注意边界条件，记录复现步骤与预期、实际行为。 | 选取相关边界，不声称穷尽所有情况。 |
| R11 | 文档和说明优先中文，必要标识保留原文。 | 保持代码与标识准确。 |
| R12 | 遵循当前范围和同一项目最新要求。 | 不将项目选择推广为全局偏好。 |
| H03 | 先做可验证版本，根据使用、测试和新证据调整。 | 本人明确回复“符合”。 |

## 场景测试补充 S01

虚构案例：MCU 与上位机串口连接间歇失败，尚无完整日志或稳定复现步骤。本人原话：“分别厅MCU和上位机进行冒烟测试，希望AI出测试案例和记录测试过程数据”。按上下文将“厅”理解为“对”。

本人明确提出的是分别对两端冒烟验证，以及由 AI 生成案例、记录过程数据。测试工具、模拟端和具体记录字段是使该方法可执行的实现建议，不是本人原话，也不是永久工具偏好。只在两端通信问题场景采用，不将其扩展为所有系统必须模拟硬件；未开展实际设备测试。

## 场景测试补充 S02

假设场景为首次学习 RTOS。本人原话：“介绍、构建最小运行系统、解析构建原理和功能说明、分析示例的作用和优缺点、自己能看懂其它的示例或手动构建一个”。

该材料补充了新技术学习的推进顺序和迁移目标。优先以最小系统组织实践和原理解释，不将入门变成无止境的前置理论讲授。读懂其他示例或手动构建是目标，并非已验证的本人能力；不能要求第一轮同时掌握完整内核或大型系统。具体环境、版本和实验设计需要另行确定，本次没有安装或运行 RTOS。

## 场景测试补充 S03

虚构案例为组件升级与保留现有版本的方案取舍。本人原话：“提供合适的方案，并说明优缺点，说明开发流程，解析方案细节，提供测试方案和结果验收”。

明确要求包括适用方案、优缺点、开发流程、方案细节、测试与验收，整理后的方案获本人回复“准确”。本人没有在此选择升级或保留旧版；推荐需要具体需求和证据。未执行测试时只能给测试设计和验收标准，不能写成已有结果；组件版本更新仍遵循先讨论的已确认边界。

## 不能从这些规则推出的内容

- 人格类型、心理动机、自尊稳定程度或关系模式。
- 当前职位、收入、学习进度等随时间变化的状态。
- 独立编写 AI 代写代码的能力，或熟练掌握某技术体系。
- 永久更新依赖、修改内核、读取敏感资料或外部发布的授权。
- 所有项目都采用同一 Git 分支方式。
- 必须为所有问题展开完整的原理追溯。

本技能可复用的是协作要求和明确认可的方法，尚未证明能重现本人在新问题上的全部技术决策。
