我按 lzy-self 的“先验证最小链路、依据实际日志缩小范围”来排查。当前没有模拟器，仍可以利用现有设备的串口日志定位故障，但单端独立验证暂时缺少证据。

这一轮只选**协议已有、不会触发运动或改变设备状态的查询请求**。帧格式和预期回复按现有协议或已知成功记录确定；如果还不明确，先找这两项，不猜测报文。

1. **确认通信条件。** 记录两端的波特率、数据位、校验位、停止位，以及本次请求的预期回复和协议规定的超时。先核对，不同时修改多个参数。
2. **只发送一次请求。** 用现有工具或程序操作，保留发送前到超时后的原始日志。至少记录时间、方向、原始十六进制字节、字节数；注明日志是在调用发送接口时产生，还是在发送完成后产生。
3. **沿链路寻找首次断点。** 若现有日志包含这些位置，就对照“上位机 TX → MCU 原始 RX → MCU 解析/处理 → MCU TX → 上位机原始 RX → 上位机解析”。没有日志的位置标记“未知”。

按观察结果决定下一步：

| 日志现象 | 当前可查的最小范围 |
|---|---|
| 上位机没有 TX | 请求是否触发、串口是否打开、写入返回值或错误 |
| 上位机有 TX，MCU 没有 RX | 串口参数、连接与端口选择、MCU 接收状态；TX 日志本身不能证明线路已发出 |
| MCU 收到的字节与请求不同 | 原始字节、长度、丢字节或分段情况；分段接收本身不一定异常 |
| MCU RX 正确，但没有回复 | 帧完整性、解析结果、命令处理状态和回复条件 |
| MCU 有 TX，上位机没有 RX | 返回方向的连接、接收状态、读取错误 |
| 上位机 RX 正确，但界面超时 | 拼帧、校验、请求与回复匹配，以及超时处理 |

找到首次断点后，只针对该处排查，再用同一请求复测。首次请求能得到正确回复后，再连续执行三次，每次等上一轮结束，检查是否出现重复操作后的超时或状态残留。
