第一轮目标是：你能独立读懂一个结构不同的消息队列示例，或依据需求手动搭出一个最小系统，并说明它为什么能工作。现有示例能运行只是起点，不能据此判断已经掌握消息队列。

目前已知你有一个能运行的 MCU 示例；未知它使用的 MCU、RTOS 或裸机框架、队列实现、开发工具及输出方式。因此先按通用机制安排，具体 API、超时单位及中断限制，后续以该示例对应版本的源码和官方文档核对。本次不安装、不运行，下面的操作与验证都是后续执行安排，尚未验收。

建议分成 3 次学习，每次约 60–90 分钟；实际进度以能独立解释和验证为准。

### 第一次：理解问题，读出最小链路

先用 15–20 分钟建立必要概念：消息队列是在生产者与消费者之间暂存消息的有界缓冲区。它解决双方执行时机不同、处理速度不同以及消息交接的问题。需要理解任务或主循环、共享数据、并发、阻塞与非阻塞，以及 C 的结构体、指针和对象生命周期；不要求先学完整个 RTOS。

从一个具体问题出发：采集端不断产生数据，处理端暂时忙碌时，数据放在哪里？只保存一个最新值、使用共享变量或设置一个事件标志，与保留一串待处理消息分别有什么不同？队列容量有限，消费者长期慢于生产者时，队列不能消除过载，必须决定等待、丢弃或反馈失败。

随后用 40–60 分钟阅读现有示例，先找出与队列有关的最小部分：

- 队列在哪里创建，容量与每条消息大小是什么。
- 谁生产消息、谁消费消息，各自在任务、主循环还是中断上下文。
- 发送和接收怎样调用，返回值怎样处理，何时等待、何时立即返回。
- 传的是消息副本还是指针；若是指针，指向的对象由谁持有、何时失效。
- 接收后的动作如何被观察，例如已有日志、计数器或调试变量。

产出一张你自己画的链路图，以及一段按执行顺序写的说明：“创建 → 生产 → 入队 → 等待或调度 → 出队 → 处理”。同时分开记录代码直接表明的事实、你对行为的预测，以及尚未查证的机制。不要把示例中的日志顺序直接等同于所有调度条件下的执行顺序。

### 第二次：围绕最小系统验证，再解释原理与取舍

安排先保留现有工具和框架，从示例中梳理出“一条队列、一个生产者、一个消费者、固定格式的小消息、已有观察通道”的最小系统。消息可包含序号和一个简单数值，先排除业务功能对观察的干扰。具体修改文件、接口和执行命令，要在拿到示例信息后写明，不能现在编造。

每项验证都先由你预测结果，再执行、记录实际结果，最后解释差异。预定案例如下：

| 输入或操作 | 观察内容 | 通过判据与证据 |
| --- | --- | --- |
| 首次启动，消费者及时接收，发送少量带序号消息 | 成功发送与成功接收的序号、内容及返回状态 | 若实现保证 FIFO，则成功入队的消息按入队顺序接收、内容一致；保留原始日志或变量记录 |
| 暂停生产，消费完已有消息后继续接收 | 空队列时接收的返回状态与等待行为 | 与所选非阻塞或有超时模式及该实现文档一致；记录状态，若测时间需注明测量方式和调度精度 |
| 控制消费者暂不取消息，尝试发送超过容量的消息 | 哪些消息成功入队，哪些发送失败或等待 | 满队列行为符合配置和返回值定义，失败不被误记为发送成功；记录发送尝试与结果 |
| 消费者恢复后再次发送 | 剩余消息、后续消息和处理计数 | 队列可继续交接消息，没有把被拒绝的消息当成已收到；记录完整序号轨迹 |
| 重新启动并重复正常与满队列案例 | 初始化状态、计数和重复结果 | 无上次运行遗留状态；结果符合相同条件下的预期 |

首次验证优先使用普通任务或主循环上下文。若原示例涉及 ISR，再单独核对是否有专用接口、是否允许等待，以及是否需要触发调度；不要把任务上下文的规则直接套到中断。

验证后回到代码解释机制：消息存储在哪、读写位置如何变化、空与满怎样判定、等待方何时变得可运行，以及实际运行还受到什么调度条件影响。关键结论要标明来自实现源码、对应版本官方文档还是本次观察；一次观察不能证明所有情况下成立。

最后讨论这个示例的设计取舍：复制小消息通常便于明确所有权，但有复制成本；传指针可以减少大数据复制，但需要管理生命周期。更大容量能吸收短时突发，却占用更多 RAM，也可能增加积压延迟。等待发送可形成反压，但可能影响任务响应；立即返回便于控制执行时间，却需要处理失败。是否适合中断、是否支持多个生产者、是否保证某种顺序，均按实际实现核对。

这一阶段的成果是：最小组成说明、预期与实测对照、队列机制说明，以及这个示例为什么采用当前设计和它的适用边界。

### 第三次：独立迁移检验

默认选择“读懂另一个示例”；如果没有可用的第二个示例，就做手动构建。两条路径都先由你独立完成，再提供反馈，不边提示答案边判断掌握。

**路径 A：读另一个示例。** 选择与原例有一处实质差异的示例，例如消息类型、生产者数量或超时方式不同。先只给源码与对应文档，让你独立交付结构图、一次正常交接的执行说明、一个异常场景预测，以及它与原例的取舍差异。再用实际代码和后续运行记录核对。判断依据是你能否找到关键机制、解释成立条件并预测具体行为，不是是否复述术语。

**路径 B：手动构建最小系统。** 只给需求：“一个来源生成带序号数据，另一个执行单元处理数据，暂时忙碌时需要保留待处理消息，资源有限，需要可观察交接结果。”不提供可直接照抄的队列调用模板。由你决定消息格式、容量、交接方式、失败处理和观察方法，写出必要代码并说明选择依据。后续验证正常交接、资源耗尽、恢复和重新启动；失败时先让你提出定位步骤，再针对证据给反馈。

第一轮通过的标准是：至少完成一条迁移路径，独立说明各部分职责、消息与内存的关系、空满及等待行为，给出合理的边界处理，并让预测与验证结果对上。若只能改参数、照抄代码或在提示下回答，就记录为“该部分仍需练习”，回到对应机制做一个更小的任务，而不笼统评价掌握或没掌握。

后续学习时，在现有项目学习文档中持续记录：环境与示例版本、最小链路、关键源码和文档位置、自己的预测、原始验证证据、问题与修正、尚未验证项。没有现有文档时再建立一份学习记录，保留原判断并追加修正。当前交付仅为学习安排；具体框架接口、执行命令、运行结果和迁移能力均尚未确认。
