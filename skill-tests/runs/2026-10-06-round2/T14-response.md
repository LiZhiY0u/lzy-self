当前可以先用现有设备的串口收发日志排查最小真实链路。缺少模拟器会限制单端隔离验证，但不妨碍先确定数据在哪一步消失或被拒绝；现在不安装工具。

已知：现有设备能输出串口收发日志。未知：协议帧格式、串口配置、日志记录位置以及故障表现。因此先选协议中已确认无副作用的查询请求；没有确认安全的查询时，先采集现有故障操作的日志，不编造测试帧，也不发送控制动作。

在现有上位机和 MCU 环境中，按以下步骤操作，每次只改变一个条件：

1. 保存当前串口配置、连接状态及故障触发步骤。双方核对波特率、数据位、校验位、停止位，以及协议已有的超时设置。先保留原配置，不同时调整多个参数。
2. 只发一次已确认的查询请求，暂停其他周期通信。记录发送前后的原始十六进制字节、方向、时间戳、字节数，以及能取得的解析或回复日志。按“上位机 TX → MCU RX → MCU 解析/处理 → MCU TX → 上位机 RX/解析”排列；某处日志没有就标为缺失，不当作该处没有数据。记录日志位于发送调用、驱动完成还是实际接收位置，因为发送调用成功不能证明线上已发送。
3. 根据第一轮结果再选一个最小复测：若一次成功，按现有协议允许的间隔重复 3 次，每次等上一请求结束再发；若一次失败，保持相同请求和配置重复采集一次，检查失败位置是否一致。若故障明确发生在重新连接后，再补一次“断开—重连—同一查询”，不用同时增加其他功能。

用这些观察缩小范围：

| 观察 | 下一步排查 | 判断边界 |
| --- | --- | --- |
| 上位机记录 TX，MCU 无对应 RX | 核对端口、串口配置、接线与接收是否启用，并确认 TX 日志位置 | 不能仅据软件 TX 日志认定物理链路正常 |
| MCU RX 字节与发送字节不同或不全 | 对比原始字节，核对配置、接收缓冲和分包处理 | 分多次接收本身不一定是故障，需按协议重组后比较 |
| MCU 收到完整请求，却没有回复 | 看解析拒绝原因、处理是否执行、回复是否进入发送路径 | 无处理日志时，解析与业务处理仍无法区分 |
| MCU 有 TX，上位机无对应 RX | 核对 MCU 发送完成证据、上位机接收状态及反向链路 | MCU 软件 TX 日志也不等于线上发送成功 |
| 上位机收到回复却仍超时或报错 | 核对回复格式、请求关联、解析状态及超时发生时间 | 超时阈值未确认前，不自行设定合格时限 |

本轮通过判据是：一次请求能按已有协议得到对应有效回复，双方收发字节能够对应，应用层确认成功，且满足已有超时要求；未知的超时阈值标为待确认。重复测试用于检查这几次是否一致，不能据此宣布长期可靠或完整验收。

把原始日志保留下来，在项目现有联调文档中补充请求、预期回复、实际结果、首个异常位置和缺失证据。可先回传一次请求的双方 TX/RX 与解析日志，并注明日志位置和串口配置；据实际输出决定下一步。目前这些是可执行的排查步骤，尚未取得测试结果，单端独立冒烟也仍待条件具备后补验。
